# Gap Analysis — current build vs the "intelligent first pass" standard

Date: 2026-10-01. Scope: the vision statement "AI preconstruction analysis + automatic takeoff +
scope analysis + exception management", measured against what is in `backend/src/ffs/` today.
Status words are used strictly:

- **Implemented**: code exists, is tested, and does the job described.
- **Partial**: a usable piece exists; the described capability is not reachable from it yet.
- **Missing**: nothing exists; the current architecture accommodates it without rework.
- **Architectural change**: something must be restructured before the capability can be built.
- **Future**: deliberately deferred; design accommodates it.

## The two sentences that matter
(certain) The current build is a document-understanding and reference-data foundation: it
turns a vector framing plan into evidenced member records with lengths, and it turns
manufacturer and UL documents into structured, versioned design data. (certain) It does not yet
reason about a project. Every capability in the vision that starts with "the system proposes"
is missing, and its accuracy is unprovable until real drawing sets exist as golden projects.

## Where the architecture already holds
- Provenance and assertion classes are first-class (`core/assertions.py`; `db/models.py`
  `assertions`, `member_evidence`, `audit_events`). Every engine above writes into the same
  structures. No change needed.
- Deterministic-first boundary (ADR-0003) matches the vision's "propose when confident,
  surface when weak".
- Reference data is versioned by document revision and fetch manifest (`sources/`,
  importers). Product switching will read it without rework.
- The review states and colour semantics exist on records and in the overlay.

## Where it does not hold (the two structural changes)
1. **Physical vs interpretation split.** `member_instances` must become the immutable
   physical layer (section, geometry, length, level, evidence). Everything else (type, scope,
   rating, exposure, condition, design, product, thickness, exclusions) becomes versioned,
   scenario-scoped assignments. ADR-0005 below.
2. **Review items as a first-class entity.** Unknowns, conflicts, missing documents,
   assumptions and RFI candidates need one table with a lifecycle, not scattered notes.
   Every engine emits ReviewItems; the queue, the meter and bid readiness read them.

## What stays exactly as it is
Ingest, designation parsing, geometry, importers, fetcher/crawler, inventory tool, golden
scoring, docs. Nothing in the vision contradicts them.

## Honest ordering
The vision's first screen ("1,842 members detected, 80 need review") depends on the member
detector being right on real drawings. Until two real golden projects exist, every engine built
on top inherits an unknown error rate. Build order therefore stays: real goldens and detector
accuracy → preflight and code profile → scope and exposure engines with the review queue →
design/thickness engine (data already in hand) → scenarios and recalculation → the rest.
